# i18n Architecture — the desk speaks the operator's language

Status: phase 1 shipped 2026-09-24 (foundation + Settings GENERAL pilot,
en/zh/ja/ko). Phase 2 wave A shipped 2026-09-25 (the desk frame + the rest
of Settings). Style and vocabulary law:
`docs/design/interface/i18n-style-guide.md`.

## The three seams

Localizing this platform is three different problems, not one:

1. **React surfaces** (`frontend/app/`) — inline literals move into frozen
   catalogs under `frontend/i18n/locales/<lang>/<namespace>.js`, one file
   per locale per namespace (size law: split before 500 lines). Components
   read them through `useTranslation`/`Trans` from react-i18next. `en`
   values are the pre-i18n strings verbatim, so the string-coupled test
   suite and e2e text locators stand unchanged.
2. **The vanilla ceremony** (`frontend/components/` — Portal, BirthCeremony,
   WitnessCommitment, WalletPicker) — locked imperative classes. The seam is
   a strings bundle threaded through the React hosts' constructor `options`
   (GatewayHost/CeremonyHost), not a rewrite. NOT YET BUILT.
3. **Backend-originated text** (notification titles, ACTS card summaries,
   REST error literals) — arrives as data and renders verbatim, so catalogs
   cannot fix it. The honest design is message keys + interpolation args
   over the wire (notification-record shape change), localized at render.
   NOT YET BUILT.

## The engine (`frontend/i18n/`)

- `index.js` — i18next + react-i18next init (operator's choice, Rule 4:
  plural grammar, fallback chains, React re-render on switch). Catalogs are
  bundled, never fetched — the desk localizes fully offline. Also imports
  the fontsource Noto Sans SC/JP/KR builds (unicode-range split, Vite-hashed).
  `setUiLanguage(code)` persists + switches; `<html lang>` follows.
  // impure
- `languages.js` — `SUPPORTED_LANGUAGES` registry (code, endonym, font set)
  + `matchLanguageTag` (BCP-47 region tags fold onto script-level catalogs).
- `language-preference.js` — the operator's choice, wallet-scoped
  localStorage via `walletKey` (`windowing/storage-scope.js`): one language
  per operator, shared by every desk window. Resolution: persisted →
  navigator → `en`. // impure
- `active-locale.js` — a leaf mirror of the active language so pure-adjacent
  formatters (`frontend/utils/format.js`, `RelinkShell/context-gauge.js`)
  follow the switch WITHOUT importing the engine (no React/i18next/DOM in
  their graph — their node-side tests stay node-safe).
- `locales/` — `common` + one namespace per desk app. Pilot ships
  `settings`; each migrated app adds its own.

## Phase 1 coverage (what is actually localized today)

- Settings window: tab bar, tablist aria, and the GENERAL tab —
  LanguageSection (the picker), AccountSection, DeskSection, SoundSection
  (chrome + board group titles/notes; the cue names ride a shared service
  and migrate with the campaign), RealmSection (incl. the `Trans` confirm
  body), DocPressSection, HotkeysSection (header/note; legend entries ride
  `services/hotkey-legend.js` and migrate with the campaign).
- Intl formatting: dates/numbers/USD in `utils/format.js` and the context
  gauge follow the active language.
- Fonts: CJK glyphs render in vendored Noto, offline-safe.

## Phase 2 wave A coverage (2026-09-25)

- **The `desk` namespace — the frame the operator navigates by**: dock
  sections/bands (`dock-groups.js` ids as keys; the alphabetical ordering law
  sorts the LOCALIZED labels via the `active-locale` leaf), every app
  registry label (`labelKey: 'apps.<id>'` beside the verbatim-en `label`;
  brand-named platform windows hold no key), `AppTitle` (labelKey + the
  being's name interpolated, never translated), window chrome aria-labels,
  the dock Start menu, wallet-disconnect confirm, the HUD lights
  (`link-status.js` returns `{key, cls, args}`; en verbatim in the catalog),
  the desk title bar (`{{name}} // PORTAL` via `portalTitle`;
  `desk-pulse.js` exports `deskChromeName`), SESSION/TURN/PROJECT/FOLDER
  header spans, and the stream window header (NEW CHAT / COUNCIL / TALK /
  SND / STANDBY / IGNITE, `voice-sitting-model.js` returning keys,
  VoiceSitting shell, sitting-strip `+ TAB`, chats rails and stamps).
- **The rest of Settings**, one namespace per tab: `settingsLook`,
  `settingsMemory`, `settingsModels`, `settingsApi`, `settingsSecurity`
  (LOOK/MEMORY/MODELS/API/SECURITY sections; `Trans` where markup is
  embedded; the `{{plural}}` slot receives '' in the no-plural languages —
  `SecuritySection.pluralSuffix`).
- Engine proof: `test/unit/desk-frame-i18n.test.js` switches the real
  i18next through ja/zh/ko and renders `AppTitle` in a real render — the
  frame's language switch is proven, not assumed.

## Exclusion zones (never localized by string-swap)

- Covenant/ToS/EULA texts — wallet-signed by fingerprint
  (`backend/services/covenant.js`); translation is a re-signing act.
- Latin founding titles — on-chain-anchored identity data.
- Tool identifiers, WS types, paths, env names, model ids, `<code>` content.

## The rollout campaign (next phases, in order)

1. **App-by-app extraction** — the remaining ~39 desk app BODIES migrate to
   catalogs using the Settings pilot as the pattern (labels maps → catalog
   keys; `en` verbatim; zh/ja/ko rows per the glossary). The frame
   (`desk` namespace) and Settings are done; app bodies (CHATS manager,
   StreamInput composer, HOUSE, WALLET, BENCH…) are what remains. Shared
   services carrying user-facing strings (hotkey-legend, execution-sounds
   labels) gain a locale seam at the same time as their first consumer
   migrates.
2. **Ceremony seam** — strings bundle via host options.
3. **Backend keys+args** — notification-record and error-code shapes.
4. **Second language wave** — th, es, pt, de, ru…: catalog rows + a Noto
   set per new script (Thai needs its own; the Latin languages reuse Inter).

## Test law

- `test/unit/i18n-catalog.test.js` guards every shipped locale: key parity
  with `en`, no empty values, interpolation-slot parity, registry coverage.
  It loads the real catalogs — no mocks.
- Suite safety comes from the verbatim-`en` law; do not "improve" an `en`
  string while extracting it. Copy changes to existing `en` strings are
  their own PRs with their own test updates.
